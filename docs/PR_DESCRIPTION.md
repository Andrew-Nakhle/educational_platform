Merges `feature/security-and-deploy-docs` into upstream `main` (`170d889`). The branch contains, in order:
`feature/local-dev-setup` → `feature/mvp-endpoints-1` … `-5` → `feature/demo-seed-command` →

**Everything is additive and backward compatible:** no URL or method was removed or renamed, and **existing
response shapes are preserved** — keys were only added, never renamed or removed. The status-code changes
listed under *Breaking-change check* replace errors (500s, 200s for missing records) with the correct code.

## Changed behaviors

- **Course status rules:** submit (draft or rejected), update (draft or rejected), delete (draft), section/lesson
  changes (course draft or rejected) → 422 with a message otherwise. Submit and approve also need at least one lesson.
- **Ratings:** a second `POST` answers 409 (as upstream); `PUT` changes a rating.
- **Missing records:** 404 `{Model} not found.` everywhere, including some that answered 200 before (admin
  approve/reject, instructor course/section/lesson lookups) and `GET /admin/users/{id}` (was 500).
- **Paid enrollment:** 503 when payments are unavailable; failed or abandoned payments no longer block a retry.
- **Profile:** `birthday` is optional on update (the stored one is kept); `PUT /student/profile` without a file keeps
  the avatar.
- **Instructor sign-up:** a used email → 422 (was 500); a rejected application re-applies (201).
- **Reset password:** an unknown email and a bad token both answer 422 `This password reset link is invalid or has expired.`
- **Rate limits:** the auth endpoints answer `429 {"message":"Too Many Attempts."}` with `Retry-After` above the limits.
- **CORS / token expiry:** unchanged until `CORS_ALLOWED_ORIGINS` / `SANCTUM_TOKEN_EXPIRATION_MINUTES` are set.
- **Stripe redirects** carry `course_id` (as upstream); the reset-password mail links to `FRONTEND_URL`.

## Breaking-change check

- **Response shapes: preserved.** No key was removed or renamed; new keys were added (listed above and in
  `PROGRESS.md`). Lists keep their old shape unless `?page=` is sent. `my-courses` keeps `courses` and adds `data`.
- **URLs and methods: preserved.** Only new routes were added; `POST` and `PUT /auth/change-password` both work.
- **Status codes that changed** (all from a wrong code to the correct one): 500 → 404/422/401 for missing users,
  used emails and API guests; 200 → 404 for missing records; new 422s for the course status and no-lessons rules;
  new 503 for unavailable payments; new 429s above the rate limits. A client that relied on the old wrong code needs a
  look; the React frontend already handles all of them.
- **Configuration:** no new required variable. The new ones (`CORS_ALLOWED_ORIGINS`, `SANCTUM_TOKEN_EXPIRATION_MINUTES`,
  `SIGNED_URL_MINUTES`, `UPLOAD_DISK`, `THUMBNAIL_MAX_KB`, `VIDEO_MAX_KB`, `FRONTEND_URL`) keep today's behavior when unset,
  except `UPLOAD_DISK`, which defaults to `b2` like the current code.

## Upstream bugs fixed

- **Duplicate `password_reset_tokens` migration:** `2026_10_24_124020_create_password_reset_tokens_table` failed on every
  fresh database because the default users migration already creates the table. It now skips when the table exists.
- **500 on a missing admin user:** `GET /api/admin/users/{id}` for an unknown id answered 500; it now answers
  404 `User not found.` (the same 404 body for every missing model).
- **API guests got a 500 instead of 401:** without an `Accept: application/json` header, a guest on an `auth:sanctum` route
  was redirected to a non-existent `login` route (500). API guests now always get `401 {"message":"Unauthenticated."}`.
- **Stripe client:** the client is created only when a payment call is made, so the catalog and the student routes work
  without `STRIPE_SECRET` (upstream moved to the same lazy approach; this branch keeps it and adds the 503 and the
  no-stuck-payment handling).
- Instructor sign-up with a used email or phone answered 500; now 422 under the field.

## How to test locally

```sh
composer install
cp .env.example .env              # Windows: copy .env.example .env
php artisan key:generate
php artisan migrate
php artisan test                  # 214 tests
php artisan demo:seed             # fake accounts (all @example.test); prints a random password once
php artisan serve
```

In a second terminal: `php artisan queue:work` (only for uploaded videos, which also need ffmpeg). Try for example:

```sh
curl -s http://127.0.0.1:8000/api/stats
curl -s -X POST http://127.0.0.1:8000/api/auth/login -H "Accept: application/json" \
     -d "email=student1@example.test" -d "password=<the printed demo password>"
```

The React frontend (`VITE_API_BASE_URL=http://127.0.0.1:8000/api`) exercises every endpoint above.

## Deployment and rollback

See `docs/DEPLOY.md`. In short:

1. **Back up the database** (mandatory before running the three new migrations).
2. Set the variables, in particular `APP_ENV=production`, `APP_DEBUG=false`, `CORS_ALLOWED_ORIGINS`,
   `SANCTUM_TOKEN_EXPIRATION_MINUTES`, `FRONTEND_URL`, `FFMPEG_PATH` / `FFPROBE_PATH`, and the Stripe and B2 keys.
3. Release command `php artisan migrate --force`; a worker with `php artisan queue:work --tries=3 --timeout=3600`
   (and `DB_QUEUE_RETRY_AFTER` above it); one scheduler (`php artisan schedule:work`) for `payments:expire-unpaid`.
4. Stripe webhook `https://<api-domain>/api/payments/stripe/webhook` with `checkout.session.completed` (and the other
   handled events).
5. Security: `php artisan tokens:revoke-all --force`, `php artisan admin:set-password <admin email>`, rotate any secret
   that was ever shared, keep the repository private, never run `demo:seed` in production.

**Rollback:** redeploy the previous version of every service. The migrations only add a column, a table and a nullable
change, so the previous code runs on the new schema; restore the backup only if a migration itself failed.
